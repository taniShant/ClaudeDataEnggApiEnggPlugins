# Component Builder — Step 7 Reference

Schema file templates and Extend mode rules for building OAS components.
Referenced by SKILL.md Step 7.

The mandatory CISO schema rules — including the **enum exemption** (enum fields must have NO minLength/maxLength/pattern) — are defined in `rules.md` as the single source of truth.
This file provides the **file templates** for generating split-file schemas.

## Per-Endpoint Schema Templates

**File naming:** Use PascalCase of the operationId as the file prefix — e.g. operationId `openAccount` → file prefix `OpenAccount`. The operationId itself remains camelCase in YAML; only the filename uses PascalCase. Directory name uses lowercase resource noun (e.g. `components/accounts/`).
- `type-OpenAccountRequestType.yaml` ← operationId=`openAccount`, resource dir=`accounts`
- `type-ValidatePaymentRequestType.yaml` ← operationId=`validatePayment`, resource dir=`payments`

### Request Type (`components/{resource}/type-{OperationId}RequestType.yaml`)

```yaml
type: object
deprecated: false
nullable: false
additionalProperties: false
properties:
  <fieldName>:
    $ref: './type-{OperationId}RequestData.yaml#/<FieldObject>'
required:
  - <required fields — flag sensitive field names as Red Flag per G7 in coordinator.md, do not silently remove>
```

### Request Data (`components/{resource}/type-{Op}RequestData.yaml`)

```yaml
<FieldObject>:
  type: object
  deprecated: false
  nullable: false
  additionalProperties: false
  properties:
    # Non-enum field:
    <fieldName>:
      type: string
      minLength: 1
      maxLength: 25                     # from design doc; 250 + comment if not specified
      pattern: '^[a-zA-Z0-9]{1,25}$'   # from design doc
      description: '<from content parser>'
      example: '<non-empty realistic value>'  # never use empty string ''
    # Enum field — no minLength/maxLength/pattern:
    <fieldName>:
      type: string
      enum:
        - 'VALUE1'
        - 'VALUE2'
      description: '<from content parser>'
      example: 'VALUE1'
```

### Response Type (`components/{resource}/type-{Op}ResponseType.yaml`)

Shape depends on what the LLD/input describes:

**Determining whether a `data` wrapper exists:** Check the input sources in this priority order:
1. If the LLD/design doc has an explicit decision (e.g. "flat JSON object, no data wrapper" or "response is wrapped in a data object") → use that. Never override an explicit design decision.
2. If the source is an Excel or tabular format showing a `data` column → only use a wrapper if the actual response body in the contract shows `data:` at the root level — not if `data` is just a column header in the table.
3. When ambiguous → use no wrapper (flat response) and flag as Red Flag.

**When response has a `data` wrapper with fields** — use a thin wrapper with `$ref` to a separate `ResponseData` file. Never inline the data fields anonymously:

```yaml
type: object
deprecated: false
nullable: false
additionalProperties: false
properties:
  data:
    $ref: './type-{Op}ResponseData.yaml#/{Op}ResponseData'
required:
  - data
```

**When response has no `data` wrapper** — define fields directly in `ResponseType.yaml`. No `ResponseData` file needed.

**When response has no body (e.g. 204)** — no type file generated at all.

### Response Data (`components/{resource}/type-{Op}ResponseData.yaml`)

Only generated when the response has a `data` wrapper with fields (see above). Same structure as RequestData. Contains the actual response fields. Include `deprecated: false`, `nullable: false`, `additionalProperties: false`.

**Rule:** When a `data` wrapper is present, its fields MUST be extracted into this named file — never inlined as an anonymous object inside `ResponseType.yaml`. The LLD or input examples determine whether this wrapper pattern applies. Downstream skills (scaffolding, forge) reference this type by name to generate the response model class.

### Response Header Schema

Headers in `responses` must include `deprecated` and `nullable`:
```yaml
headers:
  Location:
    description: 'URL of the created resource'
    schema:
      type: string
      deprecated: false
      nullable: false
      minLength: 1
      maxLength: 250
      pattern: '^/v[0-9]{1,2}/[a-zA-Z0-9/_-]{1,240}$'  # canonical — see rules.md Location Header Pattern
    example: '/v1/resource/123'
```

## Extend Mode Rules

| Situation | Action |
|-----------|--------|
| Endpoint is NEW | Generate all component files fresh. Do not touch existing files. |
| Endpoint EXISTS in existing OAS | Merge at property level — input is source of truth: input fields win, fields not in input are removed. |
| Endpoint EXISTS but NOT in `--endpoints` | Skip — do not touch. |
| Schema name collides (same name, different endpoint) | Suffix with operationId to avoid collision. |

### Merge Algorithm (property-level, existing endpoint)

Input is the source of truth. The output matches the input exactly, diff is reported.

```
merged_properties = {}
updated = []
added = []
removed = []

for field_name, field_def in input_properties.items():
    if field_name in existing_properties:
        merged_properties[field_name] = field_def   # input wins
        if field_def != existing_properties[field_name]:
            updated.append(field_name)
    else:
        merged_properties[field_name] = field_def   # new field
        added.append(field_name)

for field_name in existing_properties:
    if field_name not in input_properties:
        removed.append(field_name)                  # not in input → deleted

write merged_properties to output component file
report: updated={updated}, added={added}, removed={removed}
```

This means:
- Updated `pattern`, `maxLength`, `description` from input → applied
- New field in input → added
- Field only in existing (not in input) → **removed** (input is source of truth)
