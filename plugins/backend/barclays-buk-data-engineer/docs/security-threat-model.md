# Security Threat Model

This document records the security threats considered during the design of the `barclays-buk-data-engineer` plugin and the mitigations in place for each.

---

## Threats and Mitigations

### 1. Prompt Injection

**Threat:** An attacker embeds adversarial instructions in content retrieved from external sources — repository files, database metadata, table comments, Confluence pages, or data values — causing the agent to take unintended actions.

**Attack vectors:**
- Schema or column comments containing instruction-like text
- Data values in sampled rows that include command syntax
- Confluence pages with embedded instructions
- File content in analysed repositories

**Mitigations:**
- All content retrieved from MCP servers and external sources is treated as data, not as instructions. Retrieved content is passed to the model in clearly labelled data blocks, not injected into the system prompt or instruction context.
- Tool call policies are defined externally to the prompt. The deterministic hooks (`block-destructive-sql`, `block-secret-output`) cannot be disabled by prompt content regardless of what retrieved data contains.
- The agent does not have a general-purpose code execution capability. Tool calls are scoped to approved operations only.

---

### 2. Credential Exposure

**Threat:** Credentials, tokens, connection strings with passwords, or API keys are included in generated artefacts (code files, configuration files, schema definitions) and persisted to version control or ticketing systems.

**Mitigations:**
- The `block-secret-output` pre-write hook intercepts any Write or Edit operation containing detected credential patterns and blocks the write before persistence.
- The hook never logs or outputs the actual secret value — only the pattern type and file path.
- Generated code uses secret store references, environment variable references, or vault path references exclusively. Hardcoded credentials are never produced.
- The agent does not receive write database credentials. Only read-only access identities are provided.

---

### 3. Destructive SQL Execution

**Threat:** The agent executes DROP, TRUNCATE, DELETE, or CASCADE DDL against a live database, resulting in data loss.

**Mitigations:**
- The `block-destructive-sql` pre-tool-call hook intercepts any Bash call containing destructive SQL patterns before execution.
- Blocking is always applied in staging and production environments. No prompt override can bypass this.
- In dev/test environments, a warning is issued and execution requires explicit operator confirmation.
- The agent identity used for database access is read-only. Even if the hook were somehow bypassed, the identity lacks write permissions.
- All DDL produced by the agent is labelled as a draft artefact requiring human review before execution.

---

### 4. Sensitive Data Leakage During Profiling

**Threat:** During data profiling operations, actual personal data, sensitive financial data, or confidential values are returned and included in result manifests, logs, or generated documentation.

**Mitigations:**
- Profiling operations use aggregate statistics only by default (row count, null rate, cardinality, min/max/mean for numeric types). Actual data values are not returned.
- Sample rows are not included in result manifests or generated documents. Sample-based operations return structural information only.
- PII fields identified during classification are redacted in all output. The classification result (field is PII, classification type) is recorded; the value is not.
- Result limits prevent excessively large result sets from being processed or returned.
- The read-only access identity used for profiling has column-level and row-level access restrictions applied by the database administrators.

---

### 5. Stale or Fabricated Compliance Claims

**Threat:** The agent asserts compliance with a standard that is either outdated, has not been verified against the actual control requirement, or has been fabricated by the model without any supporting evidence.

**Mitigations:**
- The `validate-standards-provenance` post-agent hook checks every entry in `standards_applied[]` for mandatory provenance fields. Missing provenance prevents a `PASS` status.
- The evidence ledger records the basis for every compliance claim. Claims without evidence entries are flagged.
- Standards are sourced from the `barclays-buk-standards` dependency, not generated by the model. The model cites standards by their registered IDs; it does not author standard definitions.
- The unknowns register records all gaps that could not be resolved. Unresolved gaps are surfaced to the human reviewer rather than silently treated as compliant.

---

### 6. Unauthorised Data Access

**Threat:** The agent accesses data sources, systems, or metadata repositories that it is not authorised to access, either through misconfigured MCP servers or by being directed to access out-of-scope systems.

**Mitigations:**
- MCP servers are pre-approved and operate with allow-lists. The agent cannot add new MCP servers at runtime.
- The source register in the plugin lists the approved sources. The agent may only access sources on this list.
- Access identities follow the principle of least privilege. Each MCP server connection uses a scoped identity with the minimum required permissions.
- Environment separation ensures that dev/test credentials cannot be used to access staging/prod systems.
- All MCP server calls are logged in the session audit trail.

---

## Resource Limits

The following limits are enforced to prevent resource exhaustion, runaway loops, and unintended large-scale operations:

| Resource | Limit |
|---|---|
| Files read per session | 200 |
| SQL queries per session | 50 |
| Profiling result rows returned | 0 (aggregates only) |
| Recursion depth (agent self-invocation) | Not permitted |
| Token budget per agent invocation | Configured in plugin.json |
| Maximum execution time per agent invocation | Configured in plugin.json |
| MCP server calls per session | 100 |

---

## Default Deny

The plugin operates on a default-deny principle:

- Tools not explicitly listed as permitted are not available to the agent.
- Sources not listed in the source register are not accessible.
- Write operations are not available in staging or production environments.
- Any request that cannot be matched to a known task type and agent is rejected with an appropriate error rather than being handled generically.

Explicit allow lists are maintained in `plugin.json` and the source register. Additions to these lists require review by the BUK Security Review team (see `CODEOWNERS`).
