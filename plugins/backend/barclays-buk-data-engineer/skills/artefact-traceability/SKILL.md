# Artefact Traceability

## End-to-End Traceability Chain

Every artefact produced by the worker must be traceable through the full delivery chain. No link in the chain may be omitted without explicit documentation of the gap and its resolution path.

```
Requirement
  -> Source / Lineage
    -> HLD / Architecture Decision
      -> TADS Control / Risk Story
        -> Code
          -> Test
            -> Artefact / Evidence
              -> Release
```

A traceability gap at any link must be recorded in the unknowns register with impact assessment and the human responsible for resolution.

---

## Artefact Metadata (All Artefact Types)

Every artefact generated by the worker must carry the following metadata envelope:

| Field | Description |
|---|---|
| `provenance` | Identity of the generating worker, skill version and invocation reference. |
| `generated_at` | ISO 8601 timestamp of generation. |
| `input_fingerprints` | Hashes or identifiers of all material inputs used during generation. |
| `schema_version` | Version of the output schema or template applied. |
| `skill_versions` | Map of skill names to versions loaded during the invocation. |

## Mapping Traceability

All data mapping outputs must satisfy the following requirements:

- Every mandatory target field is either mapped to a source expression or explicitly recorded as unresolved with a stated reason.
- No mandatory target field may be silently omitted.
- Transformation logic is testable and unambiguous; no logic may rely on implicit platform behaviour that is not cited.
- The following attributes are captured for every mapped field:
  - Source field name, type and nullability.
  - Target field name, type and nullability.
  - Transformation expression or rule.
  - Data quality (DQ) rules applied.
  - Lineage reference (source system / dataset / table).
  - Evidence state of the mapping rule.

---

## Model Traceability

All data model outputs (logical and physical) must satisfy the following requirements:

- Logical model and physical model are separately documented and cross-referenced.
- Every entity, attribute and relationship in the logical model is traceable to the physical implementation.
- The following attributes are captured for every entity and key relationship:
  - Primary and foreign keys, with constraint definitions.
  - Data classification (e.g. PII, confidential, public).
  - Named data owner.
  - Retention and deletion policy reference.
- Physicalisation rationale is documented, including partitioning, clustering, indexing and storage decisions, each citing the standard or requirement that drove the choice.

---

## Pipeline Traceability

All pipeline and processing code outputs must satisfy the following requirements:

- Idempotency: the pipeline's idempotency guarantee is stated and testable.
- Replay: replay behaviour under failure is documented.
- Error handling: error paths are explicit, tested and linked to observability.
- Observability: logging, metrics and alerting hooks are present and referenced to the platform observability standard.
- Data quality: DQ checks are embedded, with each check linked to a DQ rule and a failing-row disposition.
- Tests: unit, integration and DQ tests are generated and linked to the pipeline component they cover.
- Configuration: all environment-specific configuration is externalised; no hardcoded credentials, connection strings or environment-specific values are present in code artefacts.
- Requirement-to-code-to-test links: each pipeline component traces to the requirement it fulfils and the test that validates it.

## Migration Traceability

All migration artefacts must document the following:

| Area | Required Documentation |
|---|---|
| Compatibility | Schema compatibility matrix between source and target versions. |
| Reconciliation | Row-count, checksum or hash reconciliation approach and acceptance criteria. |
| Cutover | Cutover sequence with human approval checkpoints identified. |
| Rollback / Fallback | Rollback or fallback procedure with conditions that trigger it. |
| Residual Data | Handling of data remaining in the source after migration; retention or deletion decision and owner. |

Migration artefacts containing destructive operations (drop, truncate, irreversible transform) must be flagged with `BLOCKED_SAFETY` handling; they cannot be executed by the worker and require explicit human approval in the change record.

## Merge Request Review Traceability

All MR review outputs must include the following for each finding:

| Field | Description |
|---|---|
| `severity` | One of: `blocking`, `major`, `minor`, `informational`. |
| `location` | File path, line range or diff hunk reference. |
| `evidence` | Exact quote or snippet from the diff that evidences the finding. |
| `applicable_standard` | Name, version and section of the standard breached or at risk. |
| `remediation` | Specific, actionable remediation instruction. |

Findings must not reference standards that are `draft`, `missing` or `superseded` without noting the status and its implication for the finding.

---

## TADS and LCT Traceability

All artefacts produced in the context of a TADS control or Logical Control Test (LCT) must satisfy:

- Business Outcome links: every TADS control mapped to the Business Outcome and LCT ID it supports.
- Risk Story links: every Risk Story linked to one or more tests that evidence its mitigation.
- Evidence links: every evidence artefact linked to the control or Risk Story it satisfies, with named owner, production date and current status (`evidenced`, `pending`, `gap`).
- No control or Risk Story may be marked `evidenced` by the worker; that status requires human attestation.
