# SDK2 to SDK3 Comprehensive Package Mapping

## Overview

This document provides a complete mapping of all package structures from SDK2 to SDK3 based on actual codebase analysis of the `accountentries-iapi` projects.

**Base Package Change:**
```
SDK2: com.barclays.api.core.*
SDK3: com.barclays.api.bap.bld.lib.*
```

**Generated packages — DO NOT migrate these imports:**
Auto-generated by `barclaysApiGenerate` from OAS specs. They are regenerated at build time:
- `{groupId}.{projectName}.generated` / `.generated.jpa`
- `{groupId}.{projectName}.downstream.{name}` / `.downstream.{name}.generated`

Only migrate hand-written source code packages listed in the tables below.

## 3. Common Response Package (`Response` class)

**Special Note:** The `Response` class moved to a different package than other response classes!

#### SDK2: `com.barclays.api.core.web.response.Response`
#### SDK3: `com.barclays.api.bap.bld.lib.common.response.Response`

| SDK2 Class | SDK3 Class | Purpose |
|-----------|-----------|---------|
| `com.barclays.api.core.web.response.Response` | `com.barclays.api.bap.bld.lib.common.response.Response` | Main response class |

**Why Different?**
- Other response classes (Message, MetaData) → `payload.response`
- Main Response class → `common.response`

#### Migration Pattern

```java
// SDK2
import com.barclays.api.core.web.response.Response;
import com.barclays.api.core.web.response.Message;
import com.barclays.api.core.web.response.MetaData;

// SDK3
import com.barclays.api.bap.bld.lib.common.response.Response;        // common.response
import com.barclays.api.bap.bld.lib.payload.response.Message;        // payload.response
import com.barclays.api.bap.bld.lib.payload.response.MetaData;       // payload.response
```

> **Usage Patterns:** See `lessons_learnt.md` Section 3 for when to use `Response` (interface) vs `RestResponse` (concrete class), including method availability matrix and complete examples.

## 4. REST Client Package

### SDK2: `com.barclays.api.core.web.util`
### SDK3: `com.barclays.api.bap.bld.lib.restclient`

| SDK2 Class | SDK3 Class | Purpose |
|-----------|-----------|---------|
| `com.barclays.api.core.web.util.RestClient` | `com.barclays.api.bap.bld.lib.restclient.RestApiClient` | REST client |
| `com.barclays.api.core.web.util.RestClientBuilder` | REMOVED | Client builder |

**Important Changes:**
- Class name changed: `RestClient` → `RestApiClient`
- Package changed: `web.util` → `restclient`
- `RestClientBuilder` removed (auto-configured in SDK3)

#### Migration Pattern

```java
// SDK2
import com.barclays.api.core.web.util.RestClient;
import com.barclays.api.core.web.util.RestClientBuilder;

@Autowired
private RestClientBuilder restClientBuilder;

@Autowired
private RestClient restClient;

Response response = restClient.callForResponse(uri, method, httpEntity);

// SDK3
import com.barclays.api.bap.bld.lib.restclient.RestApiClient;
import com.fasterxml.jackson.databind.ObjectMapper;

// RestClientBuilder removed - not needed

@Autowired
private RestApiClient restApiClient;

@Autowired
private ObjectMapper objectMapper;

ResponseEntity<String> responseEntity = restApiClient.call(
    method, uri, headers, String.class
);
Response response = objectMapper.readValue(
    responseEntity.getBody(),
    RestResponse.class
);
```

## Automated Find/Replace Rules

**These rules are used by `build-migration-agent` Phase 2 as a bulk `sed` script. ORDER MATTERS — specific class-level mappings MUST run before broad package-level mappings.**

### PASS 1: Special-case class-level mappings (run FIRST)

These classes moved to DIFFERENT sub-packages in SDK3. Must run before broad package replacements to avoid double-mapping.

```regex
# SecureField/SecureFields → logging.beans (NOT payload.beans)
com\.barclays\.api\.core\.web\.beans\.SecureField → com.barclays.api.bap.bld.lib.logging.beans.SecureField
com\.barclays\.api\.core\.web\.beans\.SecureFields → com.barclays.api.bap.bld.lib.logging.beans.SecureFields

# BufferedHttpServletRequest → logging.request (NOT payload.request)
com\.barclays\.api\.core\.web\.request\.BufferedHttpServletRequest → com.barclays.api.bap.bld.lib.logging.request.BufferedHttpServletRequest

# ReadableHttpServletResponse → logging.response (NOT payload.response)
com\.barclays\.api\.core\.web\.response\.ReadableHttpServletResponse → com.barclays.api.bap.bld.lib.logging.response.ReadableHttpServletResponse

# Specific response classes → payload.response (MUST run before bare Response)
com\.barclays\.api\.core\.web\.response\.ResponseHttpStatus → com.barclays.api.bap.bld.lib.payload.response.ResponseHttpStatus
com\.barclays\.api\.core\.web\.response\.ErrorMessages → com.barclays.api.bap.bld.lib.payload.response.ErrorMessages
com\.barclays\.api\.core\.web\.response\.MetaData → com.barclays.api.bap.bld.lib.payload.response.MetaData
com\.barclays\.api\.core\.web\.response\.Message → com.barclays.api.bap.bld.lib.payload.response.Message

# Response → common.response (LAST — prefix of ResponseHttpStatus, which is already handled above)
com\.barclays\.api\.core\.web\.response\.Response → com.barclays.api.bap.bld.lib.common.response.Response

# CoreHttpMessageConverter → payload (special path)
com\.barclays\.api\.core\.web\.CoreHttpMessageConverter → com.barclays.api.bap.bld.lib.payload.CoreHttpMessageConverter

# RestClient → RestApiClient (class rename + package change)
com\.barclays\.api\.core\.web\.util\.RestClient → com.barclays.api.bap.bld.lib.restclient.RestApiClient

# JsonUtils, ModUtils → payload.beans.util
com\.barclays\.api\.core\.web\.util\.JsonUtils → com.barclays.api.bap.bld.lib.payload.beans.util.JsonUtils
com\.barclays\.api\.core\.web\.util\.ModUtils → com.barclays.api.bap.bld.lib.payload.beans.util.ModUtils

com\.barclays\.api\.request\.validator\.RequestValidationInitializer → com.barclays.api.bap.bld.lib.restapi.bootstrap.InternalApiInitializer
```

### ⚠ Critical Behavior Change: URLEncodedUtils Fragment Parsing

`URLEncodedUtils.parse(URI, Charset)` changed behavior between versions:

| | HttpClient 4.x | HttpClient 5.x |
|---|---|---|
| Query string (`?key=val`) | Parsed ✅ | Parsed ✅ |
| Fragment (`#key=val`) | Parsed (lenient) | **Ignored** (strict) |

**Why**: HTTP fragments are client-side only — browsers handle them, they are never sent to the server. HttpClient 5.x correctly enforces this distinction.

**Impact**: If your code relied on parsing URL fragments with `URLEncodedUtils.parse()`, it must handle fragments separately:
```java
// HttpClient 4.x (worked accidentally)
List<NameValuePair> params = URLEncodedUtils.parse(uri, StandardCharsets.UTF_8);
// This would include fragment parameters — incorrect HTTP semantics

// HttpClient 5.x (correct behavior)
// Only query parameters are returned; to parse fragments, extract manually:
String fragment = uri.getFragment();  // e.g. "key=value"
List<NameValuePair> fragmentParams = URLEncodedUtils.parse(fragment, StandardCharsets.UTF_8);
```
