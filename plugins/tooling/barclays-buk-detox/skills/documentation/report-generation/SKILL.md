# Report Generation Skill
## Quick Start

This skill provides documentation generation patterns for remediation reports and corrective action docs.

```
# Loaded by detox-report-agent and detox-orchestrator-agent during the Document and Report phases.
# Generates executive-level remediation reports and JIRA tickets.
```



## Purpose

Generate a comprehensive **DETOX-REMEDIATION-REPORT** that provides a holistic, executive-level view of all CWE remediation activities for a repository. The report serves as the primary artifact for security review, audit trails, stakeholder communication, and management reporting.

## Report Template

The report MUST follow this exact structure. All sections are required (use "N/A" or "None" if no data is available for a section).

## Content Quality Standards

### Fix Descriptions

Each fix description MUST:
- Be 2-4 sentences
- Describe the BEFORE state (what was vulnerable)
- Describe the AFTER state (what the fix does)
- Explain the security impact (why this matters)
- Reference specific code elements (property names, method names, class names)
- NEVER include actual sensitive values (tokens, passwords, keys)

**Good Example:**
> Replaced hardcoded UUID `303bc7fb-...` with `${DSS_ADMIN_TOKEN}` environment variable reference. The empty default has been removed to prevent bypass with an empty token.

**Bad Example:**
> Fixed hardcoded credentials.

### Executive Summary Metrics

- **Fixes applied successfully**: Total code fixes committed (includes both pure code_fix AND the code portion of hybrid fixes)
- **Hybrid fixes**: Findings where a code fix was applied in this repo BUT additional infrastructure or external repo changes are still pending. These count toward "fixes applied" for the code portion, but also generate corrective action documents for the remaining work.
- **Attack paths fully addressed**: ALL CWEs for that attack path have been remediated (code fixes only, no pending non-code actions)
- **Attack paths partially addressed**: SOME but not all CWEs for that attack path have been remediated
- **Items skipped**: Files/components not present in this repository
- **Manual review required**: Items that need human action (credential rotation, BFG cleanup, infra changes)

### Skipped Items

Each skipped item MUST include:
- The specific component or library name (not generic "external dependency")
- The specific class or file within that component
- Why it cannot be fixed here (e.g., "source code is in a separate repository", "requires infrastructure-level change")
- A link to the corresponding corrective action document (if generated) in `corrective_actions_output/`

### Manual Review Items

Each manual review item MUST be:
- **Actionable**: "Run BFG Repo Cleaner to expunge keystore from history" (not "review security")
- **Specific**: Reference exact file names, key names, config values
- **Sequenced**: Include dependencies (e.g., "Rotate after removal", "Validate before changing")
- **Linked**: Include a reference to the corresponding corrective action document (if generated) in `corrective_actions_output/`

### Hybrid Remediation Items

Each hybrid item MUST include:
- **Code fix reference**: What was applied in this repo, including the commit SHA and a brief description
- **Infrastructure actions**: Each pending infra change listed as a concrete, actionable step with a responsible team
- **External repo actions**: Each external repository change listed with the repo name, specific file/path to modify, and a description of the required change
- **Dependency ordering**: If the external changes must happen before/after deployment of the code fix, document the sequence explicitly (e.g., "Provision vault secret BEFORE deploying the code change")
- **Linked**: Include a reference to the corrective action document in `corrective_actions_output/`
- **Verification**: Include how to verify the full remediation is complete once all parties have acted

### Next Steps

Next steps MUST be:
- Ordered by priority (blocking items first)
- Specific to this remediation (not generic security advice)
- Assigned by team/role when applicable (platform team, security team, etc.)

Typical categories:
1. Git operations (push, MR creation, message format fixes)
2. Tickets for out-of-repo fixes (specific teams/components)
3. Credential rotation (specific keys/tokens to rotate)
4. Infrastructure changes (deployment manifest updates, vault injections)
5. Verification steps (test in non-prod, validate alerting)

## Data Sources

### Primary Sources (in priority order)

1. **Git diff/log**: The authoritative source for what actually changed
2. **Threat model**: Provides attack path structure and CWE classification
3. **WIZ report**: Provides machine-detected findings with file/line detail
4. **Commit messages**: Provide CWE and attack path references
5. **Modified files**: Content reveals the nature of fixes applied

### Report metadata — Detox Version & Telemetry (header block)

- **`{PLUGIN_VERSION}`** — the detox plugin version. Read it from
  `.claude-plugin/plugin.json` (`version` field), or run
  `{python} -c "import json,os;print(json.load(open(os.path.join(r'${CLAUDE_PLUGIN_ROOT}','.claude-plugin','plugin.json')))['version'])"`.
  (`{python}` = the verified Python 3 command — `python3`, `py -3` or `python`.)
  If it cannot be resolved, write **`unknown`** — never omit the line.
- **`{TELEMETRY_STATUS}`** — the one-line telemetry outcome from the run recorder.
  Use the `telemetry_message` field returned by `scripts/telemetry/run_recorder.py`
  at Pipeline Completion (e.g. `"✅ Exported to Observe"`,
  `"⚠️  Saved locally (Observe export failed)"`, `"⚠️ Telemetry recording failed"`).
  If telemetry did not run / the field is unavailable, write **`not recorded`** —
  never omit the line.

### Cross-Referencing Logic

```
Threat Model Attack Path → CWEs listed → Files referenced
     ↓                                         ↓
Git History → Commits modifying those files → Match?
     ↓
If file modified + CWE in commit message → FIXED
If file modified + CWE in commit + infra/external actions pending → HYBRID
If file NOT in repo → SKIPPED (out-of-repo)
If file in repo but NOT modified → MANUAL REVIEW
If file modified but not all CWEs covered → PARTIALLY ADDRESSED
```

**Hybrid detection heuristic**: A finding is classified as HYBRID (rather than purely FIXED) when:
- The threat model explicitly references infrastructure or external repo changes alongside the code fix.
- The vulnerability involves secrets/credentials where the code now references an environment variable that does not yet exist in the deployment infrastructure.
- The fix requires coordinated changes across this repo AND another named repository.

## Error Handling

| Scenario | Action |
|----------|--------|
| No git history between branches | Report only from WIZ/threat model data; omit commit details |
| No threat model AND no WIZ report | Generate from git history only; executive summary shows commit-based metrics |
| File referenced in threat model not in repo | Classify as "Skipped (out-of-repo)" |
| Cannot determine CWE name | Use "Unknown CWE" with the ID |
| Git commands fail | Report what is available; note data collection limitations |
| Empty diff (no changes) | Generate report showing zero fixes with explanation |

## Constraints

- **Read-only**: Do NOT modify any source files. Only write the report file.
- **No secrets**: NEVER include credentials, tokens, passwords, or keys in the report. Redact with patterns like `303bc7fb-...` or `{REDACTED}`.
- **Accurate counts**: All statistics must be derivable from the detailed sections. If the executive summary says "7 fixes", there must be exactly 7 items in the "Fixes Applied" section.
- **Consistent references**: If Fix 1 addresses ATK-INT-02, the CWE table and executive summary must reflect this.
- **Valid Markdown**: Output must render correctly. Tables must have proper alignment. Headers must have proper hierarchy.
