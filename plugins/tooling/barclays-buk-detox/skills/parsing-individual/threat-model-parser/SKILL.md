# Threat Model Report Parser
## Quick Start

This skill provides parsing logic for extracting vulnerability data from SAST reports and threat models.

```
# Loaded by detox-parser-agent during the Parse Reports phase.
# Normalises findings from Wiz JSON and Markdown threat model formats.
```



## Purpose

Parse markdown threat model reports generated by the Claude threat model tool into a structured JSON array of normalized vulnerability findings. These reports vary in structure, using different heading levels, list formats, and table layouts. The parser must use AI-driven extraction to identify vulnerability entries regardless of the specific markdown layout, mapping each finding to the project's `Vulnerability` data model.

## Inputs

- **report_content** (required, string): The full text content of a markdown threat model report. Read from the file path provided by the orchestrator.
- **repo_root** (optional, string): The root path of the repository being analyzed. Used to resolve relative file paths mentioned in the report to absolute paths.

## Steps

1. **Read the entire markdown report** using the Read tool at the file path provided.

2. **Identify the report structure** by scanning for common patterns. Claude threat model reports may use any combination of:
   - `## Findings` or `## Vulnerabilities` or `## Threats` section headers
   - Numbered lists with vulnerability entries
   - Markdown tables with columns for severity, description, file, etc.
   - Individual `###` sub-headings per finding
   - Bullet-point lists with inline metadata
   - Mixed formats combining prose paragraphs with structured data

3. **Extract each distinct vulnerability entry** from the report. For each entry, extract the following fields:

   a. **cwe_id**: Look for patterns matching `CWE-\d+` anywhere in the entry (headings, body text, tags, table cells). If a CWE ID is referenced by number alone (e.g., "89" in a CWE column), normalize it to the `CWE-###` format. If no CWE ID is explicitly stated, infer the most likely CWE based on the vulnerability description (e.g., "SQL injection" maps to CWE-89, "cross-site scripting" maps to CWE-79). If inference is not possible with reasonable confidence, set to `null`.

   b. **title**: Extract a short title (under 120 characters). Use the finding heading, the first bolded phrase, the table row title, or synthesize a concise title from the description.

   c. **description**: Extract the full description text. Include the vulnerability explanation, attack scenario, and any impact statements. Preserve technical detail but strip markdown formatting (bold, links, etc.) from the output string.

   d. **severity**: Map the report's severity to one of the canonical values: `critical`, `high`, `medium`, `low`, `info`. Common mappings:
      - "Critical", "P0", "Severity: Critical" -> `critical`
      - "High", "P1", "Severity: High", "Important" -> `high`
      - "Medium", "P2", "Severity: Medium", "Moderate" -> `medium`
      - "Low", "P3", "Severity: Low", "Minor" -> `low`
      - "Info", "Informational", "Note", "FYI" -> `info`
      - If no severity is stated, default to `medium`.

   e. **file_path**: Extract the affected file path. Look for:
      - Explicit file references in backticks (e.g., `` `src/auth/login.py` ``)
      - "File:" or "Location:" labels
      - Table cells under "File" or "Path" columns
      - Code block annotations with file names
      - If a relative path is found and `repo_root` is provided, resolve to an absolute path.
      - If no file path is found, set to `null`.

   f. **line_number**: Extract the line number. Look for:
      - "Line \d+" or "L\d+" patterns
      - ":line_number" appended to file paths (e.g., `login.py:42`)
      - Table cells under "Line" column
      - If no line number is found, set to `null`.

   g. **remediation_type**: Classify the finding into one of: `code_fix`, `infra_config`, `dependency`, `manual`.
      - `code_fix`: The vulnerability is in application source code and can be fixed by editing code (SQL injection, XSS, buffer overflow, hardcoded secrets, etc.)
      - `infra_config`: The vulnerability is in infrastructure configuration (Terraform, CloudFormation, Kubernetes manifests, Dockerfiles, CI/CD configs, etc.)
      - `dependency`: The vulnerability is in a third-party dependency (outdated library, known CVE in a package, etc.)
      - `manual`: The vulnerability requires human judgment or architectural changes that cannot be automated (design flaws, business logic issues, etc.)
      - If unclear, default to `code_fix`.

4. **Generate a unique `id`** for each finding using the format `tm-{index}` where index is the 1-based position of the finding in the report (e.g., `tm-1`, `tm-2`, `tm-3`).

5. **Set the `source` field** to `threat_model` for all findings.

6. **Set the `tool_name` field** to `claude_threat_model` for all findings.

7. **Set the `confidence` field** based on extraction quality:
   - `1.0` if CWE ID was explicitly stated and file path + line number were found
   - `0.8` if CWE ID was explicitly stated but file path or line number was missing
   - `0.6` if CWE ID was inferred from the description
   - `0.4` if both CWE ID and file location were inferred or missing

8. **Assemble the final JSON array** of vulnerability objects and return it.

## Output Format

Return a JSON array where each element conforms to the `Vulnerability` model schema:

```json
[
  {
    "id": "tm-1",
    "cwe_id": "CWE-89",
    "title": "SQL Injection in user login query",
    "description": "The login function constructs SQL queries using string concatenation with unsanitized user input from the username field, allowing an attacker to inject arbitrary SQL.",
    "severity": "critical",
    "source": "threat_model",
    "file_path": "src/auth/login.py",
    "line_number": 42,
    "code_snippet": null,
    "remediation_type": "code_fix",
    "tool_name": "claude_threat_model",
    "rule_id": null,
    "confidence": 1.0
  },
  {
    "id": "tm-2",
    "cwe_id": "CWE-326",
    "title": "Weak TLS configuration in load balancer",
    "description": "The load balancer is configured to accept TLS 1.0 and 1.1, which are deprecated and vulnerable to known attacks such as POODLE and BEAST.",
    "severity": "high",
    "source": "threat_model",
    "file_path": "infra/terraform/lb.tf",
    "line_number": 15,
    "code_snippet": null,
    "remediation_type": "infra_config",
    "tool_name": "claude_threat_model",
    "rule_id": null,
    "confidence": 0.8
  }
]
```

**Success indicator**: The output is valid JSON, is a non-empty array, and every object contains at minimum the `id`, `title`, `description`, `severity`, `source`, and `remediation_type` fields.

**Failure indicator**: The output is empty (`[]`) when the report clearly contained findings, or the output is not valid JSON.

## Error Handling

- **Report is empty or unreadable**: Return an empty array `[]` and log a warning. Do not fabricate findings.
- **Report contains no identifiable vulnerability entries**: Return an empty array `[]`. This is not an error; some threat model reports may be clean assessments with no findings.
- **A single finding cannot be fully parsed**: Include it in the output with `null` for missing optional fields (`cwe_id`, `file_path`, `line_number`). Never drop a finding entirely unless it cannot even be identified as a vulnerability.
- **Ambiguous CWE mapping**: When the description matches multiple CWEs, choose the most specific one (e.g., prefer CWE-89 "SQL Injection" over CWE-74 "Injection" when SQL is mentioned). If truly ambiguous, pick the higher-severity CWE and set confidence to `0.6`.
- **Duplicate entries in the report**: Include all entries as-is. Deduplication is handled by a separate downstream skill.
- **Malformed markdown**: Attempt best-effort parsing. Extract whatever structure is identifiable. Do not fail on malformed reports.
- **File path references a non-existent file**: Still include the path as extracted. Validation of file existence is not the parser's responsibility.

## Constraints

- Do NOT modify the threat model report file. This skill is read-only.
- Do NOT access the repository's source code files. This skill only parses the report content.
- Do NOT fabricate or hallucinate vulnerability findings that are not present in the report.
- Do NOT re-score or second-guess severity values explicitly stated in the report. Only apply default severity when the report does not specify one.
- Do NOT attempt to fix or remediate any vulnerabilities. This skill is parsing only.
- Output MUST be valid JSON parseable by Python's `json.loads()`.
- Each `id` field MUST be unique within the output array.
- The `source` field MUST always be `threat_model`.
- The `severity` field MUST be one of: `critical`, `high`, `medium`, `low`, `info` (lowercase).
- The `remediation_type` field MUST be one of: `code_fix`, `infra_config`, `dependency`, `manual`.
- Processing should complete within the Claude Code timeout (300 seconds as configured in `config/default.yaml`).
