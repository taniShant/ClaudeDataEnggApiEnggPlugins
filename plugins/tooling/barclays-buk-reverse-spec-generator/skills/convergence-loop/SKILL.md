## 1. Core Principle

The convergence loop is the self-verification mechanism of the reverse-spec-generator. It iterates the cycle:

```
gather context ────▶ take action ──────▶ verify ─────────▶ repeat
/generate-spec        /generate-tests      /run-tests          until
→ the spec            /implement      →    /converge       →   converged
(durable context)     (spec-led items)     → .convergence.yaml
       ▲                                          │
       └───── /amend (when spec was wrong) ◀──────┘
                                                  │
                                             /status
                                        (loop dashboard)
```

The loop terminates when 100% of behaviors, rules, and constraints are aligned between spec and code.

---

## 2. The `.convergence.yaml` State File

Every `/converge` and `/run-tests` run writes a `.convergence.yaml` file alongside the `.spec` file. This is the loop's persistent memory.

**Location:** `<module>.convergence.yaml` in the same directory as the spec.

### 2.1 Schema

```yaml
version: "1.0"
spec_file: "module-name.spec"
module: "module_name"
last_run: "2026-07-12T14:30:00Z"   # ISO 8601 UTC
iteration_count: 3
convergence_pct: 72.7              # float 0.0–100.0

summary:
  total_items: 22
  aligned: 16
  diverged: 2
  missing_impl: 1
  missing_spec: 3
  unknown: 0

behaviors:
  behavior_name:
    source_of_truth: "code"        # spec | code | unknown
    test_status: "passing"         # passing | failing | error | not_run | no_test
    divergence_status: "aligned"   # aligned | diverged | missing_impl | missing_spec
    implementation_status: ""      # stub_generated | implemented (optional)
    last_verified: "2026-07-12"
    notes: ""                      # human-readable notes (optional)

rules:
  rule_name:
    source_of_truth: "code"
    divergence_status: "aligned"

constraints:
  constraint_name:
    source_of_truth: "code"
    divergence_status: "aligned"
```

**Do not edit this file manually.** Use `/amend` to set `source_of_truth` overrides.

---

## 3. Divergence Types

| Divergence type | Meaning |
|---|---|
| `aligned` | Spec and code match — no action needed |
| `diverged` | Both exist but differ — needs resolution |
| `missing_impl` | Spec says it should exist; no code found |
| `missing_spec` | Code implements it; spec doesn't document it |

---

## 4. Source of Truth Classification

Every unaligned item is classified by `source_of_truth`, which determines the correct fix action:

| source_of_truth | Meaning | Fix action |
|---|---|---|
| `spec` | Spec states intent; code must catch up | Implement or fix the code |
| `code` | Code is authoritative; spec is stale | Run `/amend` to update the spec |
| `unknown` | Ambiguous — both exist and differ | Human decision required |

### 4.1 Default Heuristic

Since code always exists before the spec is generated:

| Divergence type | Default source_of_truth | Rationale |
|---|---|---|
| `missing_impl` | `spec` | Intent was stated in spec; code hasn't caught up |
| `missing_spec` | `code` | Code implemented it before spec was written |
| `diverged` | `unknown` | Both exist and differ — needs judgment |
| `under_spec` | `code` | Code evolved beyond what spec describes |

### 4.2 Overrides

Two operations override the default classification:

1. **`/amend`** modifies a behavior's given/when/then contract → sets `source_of_truth: spec` for that item
2. **Manual edit** of `.convergence.yaml` → set `source_of_truth: "code"` to revert to code-led

---

## 5. Test Status

`/run-tests` writes `test_status` per behavior:

| Status | Meaning |
|---|---|
| `passing` | Test exists and passes |
| `failing` | Test exists and fails |
| `error` | Test threw an unexpected error |
| `not_run` | No test run result available |
| `no_test` | No test was generated for this behavior |

---

## 6. Next-Action Logic

`/status` uses these rules to determine the recommended next action:

| Condition | Recommended action |
|---|---|
| `missing_impl` or `diverged` with `source_of_truth: spec` | `/implement` |
| `missing_spec` or `diverged` with `source_of_truth: code` | `/amend` |
| `diverged` with `source_of_truth: unknown` | Human review |
| Tests failing, `source_of_truth: spec` | Fix code → `/run-tests` |
| Tests failing, `source_of_truth: code` | `/amend` spec |
| All aligned, all tests passing | Loop complete |

---

## 7. Implementation Status

`/implement` marks generated stubs with `implementation_status: stub_generated`. When the real implementation is complete and `/converge` shows `aligned`, the status advances to `implemented`.

---

## 8. Loop Termination

The loop is complete when:
- `convergence_pct == 100.0`
- All behaviors have `divergence_status: aligned`
- No `missing_impl` or `missing_spec` items remain
- All tests show `test_status: passing` (or `no_test` for non-testable items)

At 100% convergence, `/status` recommends:
1. Commit the `.spec` file as living documentation
2. Share with the team as the canonical behavioral reference
3. Schedule periodic `/converge` runs to catch future drift

## Agent Self-Check

When applying this skill, confirm:

- [ ] `.convergence.yaml` is located alongside the `.spec` file (same directory)
- [ ] `source_of_truth` is correctly set for each diverged item using the default heuristic
- [ ] `/amend`-modified behaviors have `source_of_truth: spec` in the state file
- [ ] `test_status` is updated from the latest `/run-tests` output
- [ ] Recommended next action follows the next-action logic table (Section 6)
- [ ] Loop is not declared complete until `convergence_pct == 100.0`
- [ ] `implementation_status: stub_generated` is written by `/implement` for each stub
- [ ] The state file is never manually edited except for `source_of_truth` overrides
- [ ] All `.convergence.yaml` fields conform to the schema in Section 2.1
